# FanControl 多視点レビュー（2026-10-20、ワークフロー実行）

7 つの視点（ヘルパーの安全性／書込・復元／スリープ復帰／XPC 接続／並行性／コアロジック／UI 統合）で各 1 エージェントがレビューし、指摘ごとに独立した反証担当 2 名が検証した（45 エージェント、読み取り専用）。19 件中 **7 件が確定**、12 件は反証されて却下。確定分の修正は別コミット。

## 確定した指摘

### [medium] Pinned-cdhash client identity is usurpable by any same-user process (get-task-allow + disable-library-validation on the pinned app)

- 場所: `FanControl/docs/helper.md:296`（視点: helper-security、判定: 維持 / 維持）
- 要約: helper.md §6 states that only the identical DynamicNotch binary can present the pinned cdhash and that this check is the security boundary. On this Mac the plist currently pins cdhash 6d70be39…4478, which is DynamicNotchApp/.derivedData/Build/Products/Debug/DynamicNotch.app: a user-owned (uid inu) Debug build signed with com.apple.security.get-task-allow and com.apple.security.cs.disable-library-validation (DynamicNotchApp/Support/DynamicNotch.entitlements:7, project.yml:167), embedding user-writable Lottie.framework and Sparkle.framework. The cdhash requirement covers only the main executable's code directory: NSXPCConnection.setCodeSigningRequirement validates the peer's dynamic code (directory + requirement), not the bundle seal, and library validation is explicitly disabled, so swapping a framework in the bundle or attaching to the running app via task_for_pid (allowed by get-task-allow for the same uid) yields a process that satisfies `identifier … and cdhash H"…"`. Independently, a same-uid process can simply rewrite the app's UserDefaults profile so the genuine app drives the helper. The effective boundary against same-user malware is therefore the helper's allowlist/range validation (HelperWritePolicy.validate, which does hold), not the client check; the document's claim is wrong for the realistic adversary and install.sh gives no warning for these app entitlements (it only warns about the helper's com.apple.application-identifier at install.sh:64).
- 失敗シナリオ: Malware running as the logged-in user replaces DynamicNotch.app/Contents/Frameworks/Lottie.framework/Versions/A/Lottie with an ad-hoc-signed dylib (allowed to load because of disable-library-validation) or runs `lldb -p <DynamicNotch pid>` (allowed by get-task-allow). The injected code calls openSession/writeKey over the existing XPC connection; the helper accepts because the main executable's cdhash is unchanged. It can then set F0Md=1 / F0Tg=6800 or F0Tg=Mn permanently, i.e. everything the app itself may do, without the user touching the app.
- 推奨修正: (1) Rewrite the threat-model bullets in helper.md §6 (lines 293–302): same-uid processes are inside the trust boundary in manual mode; the helper's allowlist + hardware-range validation is the control that bounds damage, and cdhash pinning only prevents a *different build* from connecting. (2) Have install.sh warn (like line 64 for the helper) when the app to be pinned carries get-task-allow or com.apple.security.cs.disable-library-validation, and document building the app to install in Release / with CODE_SIGN_INJECT_BASE_ENTITLEMENTS=NO so get-task-allow is absent. (3) If disable-library-validation must stay (ad-hoc + Hardened Runtime cannot load the embedded frameworks otherwise), say so explicitly next to the entitlement in project.yml and in helper.md.

### [medium] Helper records pre-existing FS! bits as "touched by this session" (Intel path)

- 場所: `FanControl/Sources/FanControlHelper/SessionRegistry.swift:152`（視点: write-restore、判定: 維持 / 維持）
- 要約: `performWriteLocked` does `touchedForceBits |= bits` with the whole FS! payload, but `FanWriteStrategy.writes(for:)` (FanWriteStrategy.swift:171-176) builds that payload as `(currentMask | setBits) & ~clearBits`, so bits that were already set before the session (by the SMC or another tool such as FanFi/Macs Fan Control) are recorded as this session's bits. helper.md §restore and the code comment ("FS! bits this session has set") promise only the session's own bits are cleared, but `HelperWritePolicy.restore` (HelperWritePolicy.swift:155-156) clears every recorded bit from the snapshot, and `PowerTransitionPolicy.rememberedFans` (PowerTransitionPolicy.swift:135-137) turns those bits into remembered `.forceBit` fans without a target, so `sleepHandBack` and `wakeRecovery` also hand those fans back (`wakeRecovery` line 240-245: no target → clear bit).
- 失敗シナリオ: Intel Mac, another tool holds fan 1 forced (FS! = 0b10). DynamicNotch opens a session and forces fan 0: app writes FS! = 0b11 → helper records touched = 0b11. On session close the helper writes snapshot 0b10 & ~0b11 = 0b00, returning fan 1 to automatic although this session never forced it; before every sleep and at every wake it does the same. The other tool's control is silently undone, contrary to the documented "only this session's bits" semantics.
- 推奨修正: Record only newly set bits: decode the snapshot taken for `.forceBits` (the `originals` entry) with `HelperWritePolicy.forceBits(of:type:)` and do `touchedForceBits |= bits & ~snapshotMask`. Add a `HelperWritePolicy` unit test with a snapshot of 0b10, a write of 0b11 and an expected restore value of 0b10.

### [medium] Boost preset curve (agg:cpu 50→80 °C) runs fans near maximum at idle on Mac14,9

- 場所: `FanControl/Sources/FanControlCore/Models.swift:153`（視点: core-logic、判定: 維持 / 反証）
- 要約: Boost (and the Custom 1 default) binds every fan to agg:cpu, the maximum over all Tp*/Te*/TC* keys, with minRPM at <= 50 °C and maxRPM at >= 80 °C. On Mac14,9 the hottest-core maximum is 72.7–78 °C while idle (docs/verification/Mac14,9-macOS26-probe.txt lines 39 and 228: TCMz / Tp0A = 77.97 °C; CLAUDE.md records agg:cpu 72.7 °C), so the linear curve yields 2317 + (72.7−50)/30 × 4483 ≈ 5710 RPM up to ≈ 6500 RPM at idle, versus 0 RPM under SMC control. The hardware test (first-write-2026-10-20.md test 2, curve 45→75) confirms the arithmetic: 74.35 °C → 6702 RPM. Because Boost is a read-only preset (ProfileStore ignores upsert for it), the user cannot correct the thresholds; only Custom 1/2 can.
- 失敗シナリオ: User selects the Boost preset on an idle M2 Pro MacBook Pro: both fans immediately spin to roughly 5700–6500 RPM and stay there while the machine does nothing, and the emergency/alert thresholds (90/95) never come into play. Same for a fresh Custom 1 slot before editing.
- 推奨修正: Either define Boost against a range appropriate for a max-of-cores signal on Apple Silicon (e.g. start ≈ 75–80 °C, max ≈ 95–100 °C, or use an average-based aggregate for the curve), or make the thresholds architecture-dependent via a `Preset.boostMode(appleSilicon:)` analogous to SafetyPolicy.default(appleSilicon:). Record the chosen values in docs/kit.md 'Profiles'.

### [low] helper.md section 5 still labelled "awaiting hardware retest" and omits the Md = 3 transient the retest established

- 場所: `docs/helper.md:192`（視点: sleep-wake、判定: 維持 / 維持）
- 要約: The heading `### スリープ／復帰（2026-10-20 実装、実機再テスト待ち）` and the retry rationale in the table (line 205: `復帰直後は SMC が書込を拒否しうる`) are stale: docs/verification/first-write-2026-10-20.md (再テスト) and docs/integration.md Phase 5 (line 352) record the retest as passed at 11:26 and state the real mechanism (the SMC wakes every fan at `F<n>Md` = 3 / `Tg` = 0 and resets to `Md` = 0 itself after 1-2 s, discarding writes made during the transient). helper.md's description of the wake attempts (lines 207-214) and its sample log lines therefore describe behaviour that does not match the observed first attempt (`wrote F1Md=0, F0Tg=3000` with `Md` = 3). The CLAUDE.md rule requires helper.md to stay consistent with the code and verification.
- 失敗シナリオ: A reader following helper.md section 5 expects attempt 1 to re-apply the target and treats a `wrote F0Tg=3000` followed by `observed F0 Md=0 Tg=0` at attempt 2 as a failure, or keeps the "SMC may reject writes" theory when tuning `wakeRetryDelays`.
- 推奨修正: Update the heading to the retest date/result, replace the retry rationale with the observed `Md` = 3 transient, and add the expected attempt-1/attempt-2 log pattern from the retest.

### [low] Custom profile derived from a preset drops the preset's defaultMode, so untouched fans fall back to automatic

- 場所: `FanControl/Sources/FanControlKit/FanControlManager.swift:376`（視点: core-logic、判定: 反証 / 維持）
- 要約: setFanControlMode copies only `base.modes` into the new Custom profile (`FanProfile(id: customProfileID, name: "Custom", modes: base.modes, isBuiltIn: false)`). The six presets express their behaviour via `defaultMode` with empty `modes` (Models.swift constantQuiet/constantHigh/boost), so the copy loses it: every fan other than fanIndex resolves to `.automatic` instead of the preset's mode. (Outside the Core file list, but it is a direct consequence of the defaultMode/modes split introduced in Models.swift.)
- 失敗シナリオ: Active profile is Constant High (every fan 5000 RPM via defaultMode). User sets Fan 1 to 4000 RPM from the widget. The resulting Custom profile has modes [0: 4000] and no defaultMode, so Fan 2 silently returns to SMC automatic control (0 RPM at idle) instead of staying at 5000 RPM as the UI implied.
- 推奨修正: Build the Custom profile from `base.resolved(for: fans)` (materialises defaultMode into per-fan modes) or pass `defaultMode: base.defaultMode` when constructing it.

### [low] Toggling Enable Fan Control off then on quickly leaves monitoring stopped while the feature reads as enabled

- 場所: `FanControl/DynamicNotchIntegration/FanControlGeneralTabView.swift:111`（視点: ui-integration、判定: 維持 / 維持）
- 要約: The off-path runs `defer { manager.stopMonitoring() }` inside an async Task around restoreDefaultControl (lines 110-113), which takes at least one pollQueue hop and, with a session open, several XPC writes. If the user flips the switch back on before that completes (a double-click on the switch does exactly this), the on-path's startMonitoring() runs first and the deferred stopMonitoring() then stops it. general.isEnabled stays true, isMonitoring becomes false, isSMCConnected false, and the widget shows "SMC unavailable" until the next apply or app restart.
- 失敗シナリオ: Session open on Custom 1. User double-clicks the Enable Fan Control toggle: first click starts restoreDefaultControl (async writes), second click calls startMonitoring(); restore finishes and the defer calls stopMonitoring(). Result: feature enabled, no polling, widget shows SMC unavailable.
- 推奨修正: After the awaited restore, re-read Defaults[.fanControlGeneralSettings].isEnabled (or the binding) and only call stopMonitoring() if it is still false; alternatively disable the toggle while the restore is in flight (as done for the dump button with isExportingDump).

### [low] Monitoring pause is only ever cleared by the widget's onAppear, so removing the widget (or using Settings while the Nook is hidden) leaves polling paused indefinitely

- 場所: `FanControl/DynamicNotchIntegration/FanControlWidgetView.swift:57`（視点: ui-integration、判定: 維持 / 維持）
- 要約: setMonitoringPaused(true) is called in the widget's onDisappear when pauseWhenNookHidden is on, and setMonitoringPaused(false) only in its onAppear (lines 48-59); no other code in the drop-ins or the host calls setMonitoringPaused. Once paused, the manager's timer stops entirely unless a session is open or keepAlertsWhilePaused is true, otherwise it polls every max(5x interval, 10 s) (FanControlManager.swift:975-996). If the user removes the Fan Control widget from the Nook grid (Settings > Widgets) or opens Settings > Fan Control > Sensors/Profiles while the Nook is closed, the Sensors table, key temperatures and the fan curve's live dot stop updating or update every 10 s, with "Last updated N ago" growing; sensor-linked profiles then only re-plan every 10 s as well. The pause state is also never engaged at all when the widget is not in the grid, so pauseWhenNookHidden has no effect for a user who uses only the settings pane and alerts.
- 失敗シナリオ: pauseWhenNookHidden = true (default), feature enabled, widget shown once then removed from the Nook. onDisappear pauses; nothing un-pauses. With no session and alerts on, the Sensors tab updates every 10 s; with alerts off it never updates until the Refresh button is pressed.
- 推奨修正: Drive pause/resume from the Nook open/close state (the host's notch visibility) rather than the widget's appear/disappear, and have FanControlSettingsView call setMonitoringPaused(false) in .task/onAppear (and restore the previous state on disappear) so the settings pane always sees live data.
